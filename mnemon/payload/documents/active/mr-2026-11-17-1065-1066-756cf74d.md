# 单分支模型下拆出「一功能一 MR」：流程与 2026-11-17 拆分结果

配套实现细节见既有文档 `559c3ec9-b092-48e8-bb50-e45a998e967a`（《ChatBI 评审模板导出 + 批量评审导入：实现与 MR !566/!1063/!1064》）。本文只记录该文档未覆盖的部分：**MR 混批的成因、拆分操作流程、拆分后的最终状态与坑**。

## 1. 起因（用户明确要求）

- 用户先问提交为什么这么多，随后直接定性：
  - （历史记录，m8962）"为啥你这个MR这么多提交啊 不应该只是有 导入导出的提交吗"
  - （历史记录，m8975）"你是不是放一块了啊 导入导出应该单独的MR呀"
- 结论性约定（用户提出、已按其执行）：**一个功能一批改动对应一个独立 MR，不得与未合并的上一批改动叠在同一条分支/MR 上。**

## 2. 为什么会被混在一起

- 前端仓库按 AGENTS.md 规定**每人只有一条个人开发分支**（本例 `dev/renxp4`），所有改动都累积在这条分支上。
- 上一批「评审规则页改造」的 7 个提交对应 MR !1063（→master）与 !1064（→develop），**用户尚未合并**；导入导出的提交 `71d10394` 又直接叠加在同一条分支上，于是两批改动同时出现在这两个 MR 里（`changes_count` 从 5 涨到 8）。
- 后端 !566 只有 1 个提交，本身没有问题——出问题的只有前端。

## 3. 拆分流程（可复用）

1. **量清楚现状**：`git log --oneline` 对比个人分支与上一批最后一个提交，确认要剥离的提交范围（本例只有 `71d10394` 一个）。
2. **为每个目标分支拉一次性分支**，只 cherry-pick 目标提交：
   - `feature/review-io-master` ← 从 `origin/master` 拉出，cherry-pick `71d10394` → `d349548c`
   - `tmp/review-io-develop` ← 从 `origin/develop` 拉出，cherry-pick `71d10394` → `0823b250`
3. **把原分支回退**到上一批的最后一个提交：
   - `dev/renxp4` `git reset --hard ed274278`（"评审规则页支持按真实字段值增删规则"）
   - `tmp/review-rules-develop` `git reset --hard 9f96742b`（同一改动在 develop 侧对应提交）
   - 推送用 `--force-with-lease`（`71d10394...ed274278`、`461ef888...9f96742b`），规避误覆盖他人提交。
4. **用新 MR 承接剥离出来的提交**（!1065 →master、!1066 →develop），旧 MR 自动瘦身。
5. **校验等价性**：`git patch-id --stable` 双校验两个一次性分支，均为 `3765f77a3415e5465aef815ede1e38ab85eecbf9` —— 证明是同一条补丁；再逐条确认 `merge_status=can_be_merged`、`changes_count` 已回落。

### GitLab 硬约束（决定必须换分支名）

- **同一个 `source → target` 点只允许存在 1 个 open MR。** 若沿用 `dev/renxp4 → master`，无法为导入导出再开一条 MR，所以拆分必须使用新的 source 分支名（一次性分支），而不能只改 MR 描述。

## 5. 坑（可复用）

- **`reset --hard` 会连带清掉本地未入库的联调配置。** 本例 `vite.config.ts` 里指向 `127.0.0.1:8082` 的 `/local-ask`、`/local-gpssus`、`/api/gpssus`、`/costprice` 代理被一起冲掉，需事后补回；这类本地配置必须靠 `.gitignore` 的 `*.local`（`VITE_API_BASE_URL` 留空走同源相对路径）而不是改动受版本控制的 `vite.config.ts`。
- **PowerShell 脚本内嵌中文正文会解析失败**：`restore-mr.ps1` / `update-fe-mr.ps1` 报 `Missing ')' in method call`、`TerminatorExpectedAtEndOfString`、`The string is missing the terminator: '`。中文 MR 描述一律走 UTF-8 文件 + `ConvertTo-Json`，不要内联进脚本字符串。
- **GitLab 建/改 MR 的 `description` 要 UTF-8 字节**：内联中文长文本会被判 `{"error":"description is invalid"}`（HTTP 400）；从文件 `Get-Content -Raw -Encoding UTF8` 读、按 UTF-8 字节提交即成功（实测 1308 字符正常）。
- MR 改描述后 `merge_status` 会短暂回到 `checking`/`unchecked`，需等重算后再判断能否合并。
