# 问数评审自动建单的误判与“重复提单”根因（2026-11-20 生产取证）

关联文档：`e4ce57a0-5fd7-4a73-ad84-5aa57bf3ce0f`（双时机事件驱动建单落地方案）、`2a95b6da-13f6-48f7-ace0-52cef76ec38f`（上线后批量建单现状 + 设置页 Assignee/Routing）。

## 1. 起因与结论

同事提出两点：SSGAI-1510 “步骤都没报错却自动建单”；SSGAI-1462 / 1463 “评审重复建单”。查生产库（`ssg_ops_agent`）后结论：

- 三张单**全部由程序自动创建**，无一张是人在 Jira 里手填。人工只发生在“点 Wrong 评审”这个动作上。
- 1510 是**自动规则误判**：存在“自报 failed 但零失败步骤”的轮次，落进默认判 Wrong 的分类分支。
- 1462/1463 **不是同一轮建两次**，是同一 session 相邻两轮（问题文本完全相同）各建一张，去重键决定的行为，非 bug。

**去重键 = `(session_id, turn_key)`**：两个不同 turn → 两行台账 → 两张单。1462/1463 属设计内行为。

## 3. SSGAI-1510 为何被判 Wrong

事件 `id=113769`，2026-11-19 17:28:57，`query_type=ssg_pbi_recommend`，properties：

```json
{"status":"failed","step_total":2,"step_success":2,"step_failed":0,
 "failed_step":null,"failed_reason":null,"duration_ms":18531}
```

三步工具审计全 `succeeded`：`pbi_recommend`(→`review_required`) → `delegate_task`(→`completed`) → `present_pbi_recommendations`(→`presented`，1 张卡，sheet_id=81)。功能上用户拿到了推荐。

分类表达式（`STATUS_CATEGORY_SQL`，第 462-465 行）：`step_failed = 0` 且 `status='failed'` 时落到最后一个分支 → `Failed · Failed without step details`；该规则行在 Review rules 里**默认开启且判 Wrong** → 自动判错 → 自动建单。
生产近 180 天同类分布：**19 条**（Failed 18 + Success 1）。这是噪音源规模。

## 4. 口径漏洞：FINAL_SUCCESS_SQL 不看 LUDP

`FINAL_SUCCESS_SQL`（第 877-879 行）只认两件事：事件自报 `status`，或前端拿到结果卡（`smart_data_query_result/v1` + `status=success`）。它**不检查 LUDP 权限**。而分类表达式里 LUDP 判断排第一（`CASE WHEN <LUDP_PERMISSION_SQL> THEN 'No LUDP permission' WHEN <NUM_STEP_FAILED> > 0 THEN ...`），权限会压过步骤失败。

对照两轮：

| | 234bc98b-c22c-41b8-8f3a-8f1ff06663df | 0af54804-ce80-4870-bb1f-06decbdb5302 |
|---|---|---|
| 问题 | Lenovo base warranty. | Premier Support |
| events.status | failed | success |
| failed_step / reason | revise_query / tool_business_error | 空 |
| step 统计 | 6 步：5 成功 **1 失败** | 5 步：5 成功 0 失败 |
| execute_compiled_query | succeeded，输出 `smart_data_query_failure/v1` + `ludp_permission_denied` | 同左 |
| Final result（复算） | Failed | **Success** |
| Failure category | No LUDP permission | No LUDP permission |

`revise_query` 的真实失败（非权限，`error_code=query_revision_failed`、`retryable=false`）被 LUDP 分类掩盖；而 `0af54804` 这种“只解释了一句没权限、一个数据没给”的被算成 Success。生产近 180 天 `Success · No LUDP permission` **37 条**。

## 5. 三个可选改法（未实施，等用户拍板）

| 方案 | 改动 | 影响 |
|---|---|---|
| A 源头修 | Spark 侧在 LUDP 拒绝时上报 `status=failed` / `answer_status=no_result` | 最干净，跨仓库，需等 Spark 发版 |
| B 平台口径 | `FINAL_SUCCESS_SQL` 加 `AND NOT LUDP_PERMISSION_SQL` | 两轮都变 Failed；历史 37 条统计口径变化、成功率下降 |
| C 仅展示 | 列表对 LUDP 行把 Final result 显示成 `No access` / `Blocked`，不动数据 | 零数据风险，但两字段语义仍分离 |

助手当时建议 **C 先止损 + A 排期**，理由是 B 会整体改变历史报表口径，需先确认可接受性。

## 6. 顺带查到的两处小 bug

1. **Jira 正文 `turn_id = -`**（1462/1463）：人工评审行 `ssg_chatbi_question_review.query_id` 为 null，正文取 `query_id` 而未回退 `turn_key`。修法：`COALESCE(NULLIF(r.query_id,''), r.turn_key)`，一行改动。
2. **台账 assignee 与 Jira 单不一致**（三张都如此）：台账记 `longyu3`，单上指派人 `zhangqp5`。代码 `ProbeJiraClient`（第 145-147 行）`effectiveAssignee = defaultIfBlank(assignee, properties.getAssignee)`，draft 带的是 review-assignee（`jira.review-assignee=longyu3`），建单后指派被 Jira 侧规则或人工改过。

## 8. 未决

- 1510 类噪音：建议在 Review rules 关掉 `Failed · Failed without step details` 或改为不判、交人工。
- 1462/1463 类“重复”：若想“同一问题只建一张”，需改去重口径为 同 session + 同问题文本 + N 小时内有 open 评审单则只加评论——属产品决策，改动在建单候选 SQL。
- 口径 A/B/C 待用户确认方向。
