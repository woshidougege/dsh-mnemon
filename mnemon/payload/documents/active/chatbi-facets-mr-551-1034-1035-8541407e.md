# ChatBI 反馈中心接口降级与筛选 facets（MR !551 / !1034 / !1035）

承接 **bb23dcc6-51fa-4326-866a-cd69c6d75e00**（user-logs 筛选条数）/ **4a6ba38c-451d-4a48-b625-05b6d75db712**（评审 JOIN 二义性导致同类 300）/ **2b13c2e2-62ad-49c9-b0f2-5bb15637a132**（评审筛选候选值联动）。本文记录的是 **Feedback 页 / 点踩列表面板**这一条链路的增量：300 的根因判定、附加统计降级改造、八维度 facets 口径。

## 1. 现象与根因判定（不是 SQL 的问题）

TST 上 `POST /api/admin/chatbi/events/report/feedback-records` 返回 HTTP 200 + body `{"status":300,"msg":"INTERNAL_ERROR_PLEASE_RETRY"}`。三步排除：

1. **语句本身没问题**：用 MyBatis 直连 TST 库把这条链路涉及的 8 条语句逐条真跑——`countByCondition`(70 行) / `selectPage`(10 行) / `selectSummary`(keys 齐全) / `selectReviewStats`(10 行) / `sessionSummary` / `querySessionsPageBySessionIds` / `selectUserNames` / `listProfileGroups` 全部 OK。
2. **`/report/queries/summary` 已正常**，返回 review 块（实测 `wrong:20, pending:450`）→ 说明 !548（评审参数绑定修复）已上线生效。
3. **但 feedback-records 仍 300** → 说明 !549（`FROM FROM` 修复）还没部署，而 `admin-release` head 已是 `548a62f9`（Merge `fix/review-stats-from-from`），已包含 !550。

**结论：测试环境部署的是 !548 与 !549 之间那个中间镜像**，重新从 `admin-release`（`548a62f9`）构建/重启即可；不需要再改 SQL。这类"两个 MR 之间的镜像"最容易误判为代码 bug，先用"哪个接口恢复、哪个还挂"做二分反证。

## 2. 容错改造：列表是硬依赖，其余逐段降级

原结构里用户姓名补全、轮次回查、Jira 状态、汇总、评审候选条数**任何一段抛异常都会一路穿到全局异常处理器**，前端只能看到 `INTERNAL_ERROR_PLEASE_RETRY`，连是哪条 SQL 都不知道。

改造（`ChatbiEventReportService`）：三处增强走 `runSafely`，汇总 / 会话汇总 / 评审统计走 `runOr` + 兜底值；失败打 `log.warn(..., e)` **带完整堆栈**；而 `countByCondition` + `selectPage` 仍是硬依赖，真出问题照常报错。

原则：**"列表本体"与"附加统计"要分级**——附加统计坏掉应当退化为"没有数字"，而不是让整页 500。以后排查直接看日志里那条带堆栈的 warn。

## 3. 筛选 facets：八个维度补齐条数

之前只有 User + 评审 4 项有数字，Type / Band / L3 / L4 / L5 / Team / Reason / Jira status 八个下拉全是纯文案。现改法：

- 后端新增 `selectFacetStats`，八个维度各一段 `UNION ALL`，返回 `{dim: {value: count}}`（改动落在 `admin/usagefeedback`：`AdminFeedbackTimelineMapper` + `UsageIssueFeedbackService`）。
- **口径契约（关键）**：只跟 **时间范围 + 搜索词 + Include internal users** 走，**不叠加维度自身的勾选**——否则勾掉一个 Band，别的 Band 立刻变 0，下拉就自锁了。
- TST 实测：`kind / band / l3 / l4 / l5 / team / jira` 各维度合计 **55**，`reason` **38**（只有点踩行有原因码），与 Total feedback 对得上。

前端（仓库 `ssg_sales_ops`，`src/services/usageIssueFeedback.ts` + `src/views/Setting/reports/usage-issue-feedback/index.vue`）：下拉拼 `· N`；顺手删掉死代码 `reviewerCount`（eslint `no-unused-vars`）。默认 `includeInternal = false`，与 user-logs 的 Data scope 口径一致——点踩目前几乎全是内部账号，空态里要明确提示勾选 "Include internal users"。

## 4. 测试：SQL 渲染断言 + 降级路径断言

- `AdminFeedbackTimelineMapperSqlTest`（8 例）用 `MapperSqlRender`（`renderAll()` / `sql(method)` / `sql(method, overrides)`）渲染真实 mapper 的 SQL 做断言，不连库。核心契约：
  - 明细 / 条数 / 汇总共用 `FILTER_SQL`，但要区分：`selectAdminFeedbackTimeline` 与 `selectAdminFeedbackTimelineStats` **含** `c.review_status IN`，`selectReviewStats` **不含**任何 `review_status / review_tag / reviewer_itcode / review_source` 条件（否则勾 WRONG 后 CORRECT 条数就是 0）。
  - `selectReviewStats` 仍受非评审维度收窄（`hc.band IN`、`c.kind IN`）。
  - `PENDING` 的语义 = 点踩但无评审行 → `c.kind = 'downvote' AND c.review_status IS NULL`。
  - 空列表不生成条件（渲染结果与 baseline 全等）；`jiraFilters=__no_ticket__` → `c.jira_key IS NULL`；`reasons` → `jsonb_array_elements_text`。
  - `MapperSqlRender` 内置 `assertNoDoubledKeyword` / `assertNoGluedKeyword`（`GLUED_QUOTE` / `GLUED_IDENTIFIER` 正则），就是 `FROM FROM` 那类粘连关键字的回归防护。
- `ChatbiEventReportServiceFallbackTest`（1 例）：评审统计 + 汇总 + Jira 状态**同时**失败时列表仍返回。合计 9 例全绿。
