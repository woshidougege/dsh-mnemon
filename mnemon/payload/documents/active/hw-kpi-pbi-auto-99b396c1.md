# HW KPI 折线标签三段式退让终态 + PBI 标签语义核对（Auto 实测无增益）

主题文件：`src/views/Bookings/components/miniTable.vue`（Bookings 与 GPSSUS 页共用）。
前置文档：`085a5e2b-9be3-4cdf-aa9e-59c676943cc2`（最底线条零标签根因 + 只往上退让）、`1307beef-abaa-4421-b44a-5a18bc9a2cde`（标签样式终态 + 避线四方案调研）、`0200947d-78c0-4b83-905e-cacea7c7ad11`（图上带单位落地）。本文记录这三篇之后的**退让策略终态**与一次**失败的模仿尝试**，本文的"三段式"取代 085a5e2b 里"四位置全死时只在上方允许压线"的旧描述。

## 1. PBI 折线图标签的真实能力（用户反复追问后的核对结论）

用户连续三轮质疑"PBI 是不是会把数值避开线、放到左上/右上/左右"，核对结果是**不是**：

- Position 下拉只有四个值：Auto / Above / Below / Center，且是**整张图选一个**，不是逐点决定；折线图**没有 Left/Right**，也没有 "Best fit"（best fit 是饼图/环形图的选项）。
- Auto 的行为只是：看点落在绘图区上半还是下半、标签会不会出界，在"上"和"下"之间二选一，**连左右都不考虑**。
- "看起来干净"靠两点叠加：① 标签与**标签**重叠或超出绘图区时**直接不渲染**（窗口拉大数字变多、缩小变少）；② 可开标签背景（纯色块盖住穿过的线）。
- PBI **不做标签与折线的求交**，因为它不知道线在哪里；标签只按固定偏移绘制。所以"像 PBI 一样避开线"严格说不存在——我们反而比 PBI 多做了折线采样碰撞检测（沿折线采样 11 个点判包围盒）。

## 2. Auto 模式实测：无增益，未采纳

设想实现：在 `pickPlacement` 里先看点在中线上下，决定先试上还是先试下（一行判断，不动结构）。用真实数据对比结果：

- Geo 视图（6 条线 × 11 季）：固定顺序（先上 13 → 下 13 → 上 22 → 下 22）**23 个标签 / 6 个压线**；半区 Auto **23 / 6** —— 完全相同。
- 原因：候选位本来就同时包含上方与下方，先试哪个不改变"最终哪个能放下"；书签类卡（Bookings/Qty，线间距 > 30px）上下都放得下，更无差别；Geo 这种 6 线挤在 1~4 区间时，Auto 只是换了"谁先占位"，低值区反而更容易互撞。

结论：**Auto 不落地**；白色背景块与白色描边在白色卡片上视觉等效，同样不采用。真正有效的是"放不下就不画"这条 PBI 规则。

## 3. 三段式退让（当前终态，commit `9184ec1d` "refactor(bookings): 标签分三段退让，尽量别压到别的折线上"，+21/−10）

1. **第一档**：`fits("strict")` —— 不压任何线、不重叠、不出界；
2. **第二档**：只允许压**自己那条线**（`hitsLine(b, di)`），2.5px 白色描边保底可读，数字归属不会被误读成别的序列；
3. **第三档**：只有**关键点**（首季 / 峰值 / 最近一季）才允许压任意线（`hitsLine(b)`），因为这几个值业务必须看到。

**非关键点停在第二档，宁可空着也不强行放置** —— 即 PBI 的"放不下就不画"。此前"四个候选位全死就一律允许压线"的版本（commit `dd9b7d5f`）会被这一档取代，它就是出现 `$2.4B` 掉到 ISG 线旁的原因。

## 4. 实测效果（Geo 视图，本地按卡片比例渲染）

| | 改前（一律允许压线） | 改后（三段式） |
|---|---|---|
| 标签总数 | 23 | 25 |
| 压在别的线上 | 6（不分点位） | 4（全是关键点） |
| 压在自身上 | — | 4 |

Bookings 的 ISG 序列 0 → 3 个标签，Qty 的 ISG 得到完整一排 K 值（`44.5K/48.6K/52.6K…`）。
