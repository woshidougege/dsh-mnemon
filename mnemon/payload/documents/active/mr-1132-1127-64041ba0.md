回放翻译整会话：为什么不能一次全发、以及现在实际怎么切

前序：`3ac2a628-0a6a-42ed-a2a3-56755ff27ed0` 记录到「只翻当前 turn / 整轮替换」为止。本次是在其之上再加第二个按钮——一键翻译整个会话，以及用户紧接着追问「不能一次都发给大模型吗」后给出的容量结论。

## 需求口径

标题栏共两个按钮：一个翻当前轮（跟随视口的那一问），一个翻整篇。用户问的「必须一个会话一个会话地翻译吗」是误解——实际既不是按会话、也不是按轮次切，而是按**文本量**切。

## 结论：一次全发在当前模型接口下不可行（不是带宽/token 余额问题）

| 位置 | 限制 | 含义 |
|---|---|---|
| `smartop-service/admin/src/main/java/com/lenovo/admin/chatbi/service/ChatbiReplayTranslateService.java:59` | `MAX_REQUEST_ITEMS = 120` | 一次 HTTP 请求最多 120 段，超出直接 400 |
| 同文件 `:55` | `MAX_CALL_CHARS = 12000`、`MAX_CALL_ITEMS = 24` | 单次模型调用的输入上限 |
| 模型配置 | `max-tokens 8192` | 输出上限，折合 6000~8000 字符译文 |
| 同服务 | 单次调用超时 180 秒 | 长输入更容易漏段、串行错位、破坏 Markdown |

一个 124 轮的会话正文约 20~40 万字符，全量一次翻译需要同等量级的**输出**，是单次上限的 50 倍左右 —— 属于结构性不可能。附带风险：长输入下漏段/串行错位/Markdown 结构被破坏的概率随长度上升；一旦失败整篇结果作废，必须从头再来（这也是「分批才有部分成功」的另一个理由）。

## 实际的分层切分（四层，用户只点一次）

1. 前端 `translateWholeSession()` 收集整会话所有轮次文本，**全局去重**（同一句模板话术只付一次钱，如 "70 rows · 3 columns"）；
2. 每 20 轮合成一块，一块发一次 HTTP；
3. 每次 HTTP 内部再按 12 段 / 8000 字符切；
4. 后端按 12000 字符 / 24 段切模型调用。

124 轮约 = 30 来个 HTTP、20 来次模型调用，串行约 3 分钟。

## 整会话按钮的实现取舍

- `sessionTurnIds`：按出现顺序遍历 `messages`，只取 `role === 'user'` 且 turnId 非空并去重——轮次的权威列表来自 user 消息，不是 assistant 消息。
- 先建 `plans: Array<{turnId, texts}>` 再建去重后的 `jobs`（`t-${index}`）。返回后用 `sourceById` 把译文映射回原文串，再按 plan 拆回每轮的 `PbiTextMap`，写回 `translations[\`${prefix}:${turnId}\`]`。这样「去重提交」与「按轮存储」两个需求不冲突。
- **每批完成即生效**：每批返回就写入 `translations`，用户能看到会话从前往后逐段变中文；某一批失败只影响那一批，标题栏提示 "N block(s) failed"，不丢前面两分钟的结果。
- 完成态只在语言未变时置位：`if (langPrefix() === prefix) { allTranslated = true; allOriginal = false; originalTurns = {} }`。切目标语言后整篇的"已翻完"作废，因为译文按语言前缀各存一份。
- 三态文案与互斥：未翻 `Translate all`（进行中显示 `Translating 40/124`）→ 已翻完 `Original all` → 正看原文 `Translation all`；单轮按钮与整篇按钮任一进行中互相禁用（`if (allTranslating.value || translating.value) return`）。整篇按钮用描边样式，避免与当前轮主按钮抢视觉。

## 后续可选优化（已向用户提出、尚未实施）

1. **前端并发 3~4 路**：现在 30 来个请求串行，并发后总时长可从约 3 分钟压到 1 分钟内；代价是后端瞬时压力大、失败重试粒度变粗。
2. **后端异步任务**：点一次提交 taskId，关弹窗仍在后台跑，回来能看结果。改动更大，但"一次全发"的体验才真正成立。
