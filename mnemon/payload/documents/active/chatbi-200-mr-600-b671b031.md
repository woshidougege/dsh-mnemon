# ChatBI 报表「接口 200 但数据块为空」两个根因的修复验证（MR !600）与首屏分块出数方案（待决）

承接三份已有文档：
- f4ea3686-cfb6-4cd9-9e97-913d85d292bc：QUERY_PARALLELISM 6→18 与 Guava 60s 缓存的实施实测；其中第 4 节「顺带发现的两个既有 bug」正是本文修掉的两项。
- 664308d6-d2cc-47b5-a77e-c544492e5504：会话记录报表 6 条并行 SQL 的 EXPLAIN ANALYZE 归因（三层 LATERAL 逐行展开 7753 行、hit=274k、RTT 233ms 测法、不建议合并 SQL 的理由）。
- f3474585-e700-4c3c-9a68-df5abd42e039：报表加载态动效；其第 4 节描述的「指标卡骨架屏」实现已被后续改动推翻，见本文第 6 节。

## 1. 两个根因（共同症状：HTTP 200、页面数据块空、日志被 catch 吞掉）

### 1.1 参数名漂移：@Param 与 XML #{} 对不上
- ChatbiEventReportService 的 26 个报表查询方法里，只有 sessionInternalCount 一个把参数写成 @Param("mode") / @Param("band")，而同文件 MyBatis XML 一律用 #{chatbiMode} / #{bandLevel}。
- 后果：只要调用就抛 Parameter 'chatbiMode' not found，被 service 侧 catch 吞掉 → internalCount 永远是空，接口照旧 200。
- 修复：ChatbiEventQueryMapper.java:1408-1410 的 @Param 改名为 chatbiMode / bandLevel（对齐 XML 与其余 25 个方法）。
- 可复用诊断模式：这类失败不产生 5xx，只在日志里留一条 BindingException —— 报表「某些数字一直是 0/空」优先去日志 grep "not found"，再对照 @Param 与 #{...} 的拼写。

### 1.2 别名引用缺关联：只在 keyword 非空时才炸
- 三条语句 sessionSourceStats / sessionTopQuestionsBySource / sessionStatusCounts 的 keyword 条件里引用 sn_profile.v / sn_user.v / sn_jira.v，但 FROM 段没有对应 LATERAL 关联。
- 后果：搜索词为空时正常，填了搜索词就报 missing FROM-clause entry for table "sn_profile"，同样被吞 → 结果是「带搜索条件时数据块空」这种看似随机的不一致。
- 修复：ChatbiEventQueryMapper.xml 三条语句各补 sn_jira / sn_profile / sn_user 的 LATERAL 关联。

## 2. 全量核对方法（比逐条看日志可靠）
写脚本对 51 条语句做两两校验：
1. 每条 #{参数} 是否存在对应的 Java @Param 名（重载方法按参数顺序对齐）；
2. 每个出现的表别名是否在同一语句里真有 FROM / JOIN / LATERAL 定义。
跑完 0 处不一致。若再加语句，这套校验应作为回归闸门，而不是等线上出现空数据块。

## 7. 后端串行链（为什么 KPI 卡也慢）
ChatbiEventReportService.java:354-410 的 feedbackRecords 在单个请求里顺序执行 8 步：count → 分页明细 → 补用户名 → 回查轮次 → 补 Jira（1-5 供表格）、selectSummary（6，KPI，轻）、sessionSummary（7，LATERAL 展开 7753 行，1.8~4.7s）、selectReviewStats（8）。
关键浪费：第 7 步整条重聚合只为了取 askQuestions / askUsers 两个分母（:380-393），却排在 KPI 之前，导致最轻的卡片要等最重的查询。代码注释里已说明它是故意复用 sessionSummary 以保证与「问数记录」同口径（时间范围 + 用户筛选 + includeInternal + Band / Job Family / 汇报线），口径不能改，只能挪位置或拆接口。

## 8. 备选方案与取舍（用户尚未拍板）
1. 档 1 · 静态结构化占位：LoadingRows 从转圈改回「静版」占位（metric 画 N 张卡片框：标签条/数字条/说明条三层；rows 按真实列数画格子），完全静止、不做 shimmer。1 个文件、约 30 分钟。理由：骨架屏此前因「灰条闪烁」被换成转圈，静止骨架能同时避开"空"与"闪"。
2. 档 2 · 后端并行 + 拆接口：① 表格链(1-5) 与汇总链(6-8) 用 CompletableFuture 并行；② 另开 /feedback-records/summary 只返 KPI。约半天，总耗时 5.2s → 2~3s，卡片区 ~0.5s 先出。
3. 档 3 · SSE 逐块推送：首屏等于最快那块，但要改网关 buffering，边际收益小，暂不做。
4. 更便宜的一招（不需要拆接口）：把第 7 步的 sessionSummary 移出主流程 —— 反馈侧数字 200ms 就有，覆盖率 / 差评率两个比值后到、单独淡入。
推荐组合：档 1 + 档 2；若只做一件事，先做第 4 条（改动最小、首屏立刻见数字）。
