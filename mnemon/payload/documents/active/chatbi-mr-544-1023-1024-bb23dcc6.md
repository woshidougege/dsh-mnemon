# ChatBI 用户日志报表：筛选下拉「显示可筛条数」实现（MR !544 / !1023 / !1024）

前置：评审筛选候选值联动（!542 / !1021 / !1022）见 **2b13c2e2-62ad-49c9-b0f2-5bb15637a132**；「问题轮」口径契约见 **53c4bc18-6900-4cfa-9b75-d36a82197291**。本文只记录**条数（count）联动**这一增量。

## 1. 问题与根因

页面：SSG ChatBI「用户日志 / 会话记录」报表筛选条。用户提出：下拉为什么只有一部分选项带数字。

- 级联下拉的基础数据是 `(user, mode)` 组合，后端 `listUserModePairs` / `listSessionUserModePairs` 原本用 `SELECT DISTINCT`，只剩去重值的集合，**数不出条数**，所以 User / Mode / Band / Team 这类维度没有数字。
- 原先只有 L3/L4/L5 带数字，因为那是「按人数 tally」单独算出来的。
- Status category / Result / Rating / Result source 四个走前端另一套 `decorated()`，本来就有条数（见 `FilterBar.vue:146-149`）。

## 2. 后端改动（3 个文件，+61/−14）

- `smartop-service/admin/src/main/java/com/lenovo/admin/chatbi/dao/ChatbiEventQueryMapper.java`：`listUserModePairs` / `listSessionUserModePairs` 从 `SELECT DISTINCT` 改为 `GROUP BY user, mode` 并带出 `count(DISTINCT session_id)`。
- `smartop-service/admin/src/main/java/com/lenovo/admin/chatbi/service/ChatbiHcService.java`：`cascade()` 把每行 count 按维度累加，随 options 下发 `userCounts` / `modeCounts` / `bandCounts` / `jobFamilyCounts`。
- `smartop-service/admin/src/main/java/com/lenovo/admin/chatbi/service/ChatbiEventReportService.java`：把上述计数透传到报表汇总响应。
- **口径统一**：L3/L4/L5 的 count 由「人数」改为「会话条数」，文案 `N users` → `N rows`——避免同一条筛选里出现两种计数单位。

## 3. 前端改动

- `src/views/Setting/reports/user-logs/components/FilterBar.vue`、`ManagerCombo.vue`：User / Mode / Band / Team 选项文案后拼 ` · N`（**不置灰**，只显示数字）；人员下拉副标题从纯 itcode 变成 `itcode · 条数`。
- 评审四个筛选（status / tag / source / reviewer）在已有的「只列有数据」基础上接上条数：`onlyWithData(list, counts)`（`FilterBar.vue:175-178`）先滤掉 0 条的项再拼数字，与 `reviewStatusList` / `reviewTagList` / `reviewSourceList`（:180-182）和 `reviewerList`（:187-196，直接取评审表实测、不回退用户字典）并行不冲突。

## 5. 仍未补条数的 6 个维度（用户当次未决定是否一起做）

Data scope(Profile) / Department / Org level / Jira status / Page / Executive flag·line。

原因：这些维度的数据源不是同一口径（LDAP、静态目录、反馈表各一套），要补就得各加一条统计查询，不能复用 `cascade()` 的 `(user, mode)` 计数。用户当时的选择是「先这样发版看效果」。
