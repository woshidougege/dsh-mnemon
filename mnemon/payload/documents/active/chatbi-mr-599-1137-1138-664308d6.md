# ChatBI 会话记录报表接口性能归因与优化方案（2026-11-20）

前置：来源七态口径与 !577/!1076/!1077 交付见 **6c0e9cea-ef5e-4642-bf38-1aba552f7258**；筛选下拉条数联动见 **bb23dcc6-51fa-4326-866a-cd69c6d75e00**。本文只记录本轮（!599/!1137/!1138 批次）的性能测量与优化取舍。

## 1. 测量前提：先量固定开销再扣

- 用户日志/会话记录页一次加载并行发 6 条 SQL（线程池 QUERY_POOL，父对话定位到 ChatbiEventReportService.java:1188），端到端体感 3–6 秒。
- 本地连库有固定网络延迟，所以先量出来：`select 1` 采样 5 次 → [246, 233, 233, 232, 232] ms，**固定 RTT = 233ms**。
- 每条 SQL 只往返一次（6 条并行），因此 **端到端 ≈ 最慢那条 SQL 的 DB 时间 + 233ms**。
- 用 `EXPLAIN (ANALYZE, BUFFERS)` 在库上跑真实 SQL（筛选参数全空 = 页面全部选 All），只看服务端 Execution Time，网络已排除。

## 2. 实测数据（6 条中 4 条核心）

| SQL（ChatbiEventQueryMapper.xml） | wall | DB Execution | 逻辑读 Buffers |
|---|---|---|---|
| :154 sessionSummary（核心指标） | 5969 / 2588 ms | **4721 / 1786 ms** | hit=123k~125k（≈1GB） |
| :158 sessionReviewStats | 2275 ms | **2022 ms** | hit=181k |
| :166 sessionSourceStats（来源表） | 2824 ms | **2316 ms** | **hit=274k** |
| :170 topQuestions | 242 ms | 0.047 ms | 无效，见 §5 |

结论：**接口端到端 ≈ 2.5–3 s（缓存热）/ 5–6 s（缓存冷）**，其中 233ms 网络固定开销只占约 8%，**不是主要瓶颈**。

## 3. 瓶颈定位：三层 LATERAL 逐行展开

:154 计划骨架（热缓存那次）：

`Q
Aggregate 1785ms
  └ Sort 1651ms (rows=7753)
      └ Nested Loop Left Join 1636ms
          └ Nested Loop Left Join 1628ms
              └ Nested Loop Left Join 1573ms
                  └ NL 88ms (rows=7753)
`Q

- **跃变点在 88ms → 1573ms**：7753 行结果集每行各查一次 `ssg_chatbi_report_route`（报表来源判定）与 `agent.tool_audit_logs`（成功判定）。
- Sort 自身只占 15ms（1651−1636）——**不是排序慢，是排序前先把 7753 行逐行展开**。
- :166 更极端（hit=274k）：LATERAL 里再套 LATERAL，重复扫描最严重。

对照实验（证明「单表 EXISTS 不是问题」）：audit 行总量 62096、成功 60666；A = 现写法 EXISTS 341ms（total=8635 / success=4554）vs B = CTE 预聚合 + LEFT JOIN 285ms。**成本来自带条件分支的 LATERAL 展开，不是 EXISTS 本身。**

## 4. 优化建议（按收益排序，含取舍理由）

1. **接口级结果缓存（收益最大、改动最小）**：key = 全部筛选参数 md5，TTL 60–300s。刷新、切 tab、翻页都在重复打同样 6 条 SQL；分析型报表能接受分钟级延迟。预计 3s → <100ms。注意该查询路径**当前不走 Redis**（纯 PG + 内存聚合），要做这一步得先加缓存层。
2. **把 :166 与 :154 的 LATERAL 提成 CTE 预聚合**：先按 session 聚合一次再 LEFT JOIN 回主表，Nested Loop 会退化成 Hash Join，hit=274k 这种量级可砍掉一个数量级。预计 2316ms → 400–600ms。
3. **work_mem 检查**：Sort 7753 行未明显 spill，但 :158 的 GroupAggregate 按 9 个 COALESCE/CASE 维度分组、rows=83 仍偏慢；若 work_mem 是默认 4MB，调到 32–64MB 让其走内存。
4. **不建议合并 6 条 SQL**：看着「6 次扫描合成 1 次」很美，但合并后单条要算全部聚合，串行跑完可能 5–6s，比现在并行 2.3s 更慢。**保持并行是对的。**
5. **RTT 233ms 不用管**：只出现一次，摊在 3s 里约 8%；真要优化只能是服务部署到离库近的机器，收益远小于 1、2。

## 5. 遗留 / 待确认

- **:170 topQuestions 没测出有效数据**：测量脚本的模板替换把必要条件弄成 NULL，直接返回 0 行（planLines=7，Execution 0.047ms）。补测需一个真实筛选组合的参数值。
- 测量脚本教训：带参 SQL 不能简单字符串替换——把 `#{...}` 替换掉后，4 条大 SQL 全部报 `syntax error at or near "{"`（位置 6522 / 6070 / 5603 / 4826）。线上 SQL 本身没问题，是测量方式的问题；要复现须注入真实参数值。
- 输入侧核对过：controller 共 23 个 `<if>` 标签，参数集合为 from/to/itcode/event/env/chatbiMode/keyword/sessionId/bandLevel/l3Mgr/l4Mgr/l5Mgr/jobFamily/sessionResult/sourceReport/statusCategory/reviewStatus/reviewTag/reviewer/reviewSource。
