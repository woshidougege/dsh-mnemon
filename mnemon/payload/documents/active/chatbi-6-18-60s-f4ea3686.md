# ChatBI 会话汇总报表：线程池扩容 + 60s 结果缓存（已实施并实测）

状态：**已改完并在本地跑通实测**，改动仅 1 个文件 48 行（未提交，留在工作区）。前置归因分析与优化建议见关联文档 `664308d6-d2cc-47b5-a77e-c544492e5504`（本文只记录实施结果、实测数字与遗留问题，不重复 EXPLAIN 归因）。

## 1. 改动（唯一文件）

`smartop-service/admin/src/main/java/com/lenovo/admin/chatbi/service/ChatbiEventReportService.java`

| 改动 | 内容 |
|---|---|
| 并行度 | `QUERY_PARALLELISM` 6 → **18** |
| 结果缓存 | 新增 Guava `SUMMARY_CACHE`：`CacheBuilder.maximumSize(200).expireAfterWrite(60, TimeUnit.SECONDS)`，类型 `Cache<String, Map<String,Object>>` |

没动 SQL、没动 Mapper、没动前端。

**为什么是 18 而不是 6**：单个请求就要占满 6 条查询，池子只有 6 时第二个用户点查询必须排队等前一个跑完（当时实测 1 人 3s、2 人 6s、3 人 9s，静默排队且不报错）。18 = 3 个请求 × 6 条，天花板卡在 Druid `maxActive=20` 以内——18 条查询线程 + 2 条留给非报表接口（登录、下拉候选值），再往上加会先吃干连接池，变成别的接口等报表。线程池保留 `CallerRunsPolicy`：队列满时退回调用线程执行，宁可这次退化成串行，也不丢查询、不无限排队。

**缓存口径**：只在成功返回处 `SUMMARY_CACHE.put`，不缓存异常路径。key 由 `summaryCacheKey(...)` 拼接 **22 个筛选参数**（from/to/itcode/event/env/keyword/mode/includeProbe/band/jobFamily/l3Mgr/l4Mgr/l5Mgr/sessionResult/statusCategory/sourceReport/includeInternal/sessionId/reviewStatus/reviewTag/reviewer/reviewSource），null 与空串等价（都是「不限」），用 `|` 分隔而非 JSON 以省一次序列化。理由：埋点本身是分钟级延迟的分析口径，60 秒陈旧窗口不会让看板说错话；200 条上限保证筛选组合再多也撑不爆堆。

## 2. 实测数据（本地，admin 监听 8082）

| 场景 | 耗时 |
|---|---|
| 首次请求（冷） | **12324ms**（含 Druid 首次建连 + JVM 冷启动） |
| 第 2 次 | 597ms |
| 第 3 / 4 次 | **247 / 245ms**（缓存命中） |
| 基线 `/menu/all`（白名单，不跑报表 SQL） | **392ms**（框架 + 鉴权查库地板） |
| 3 路并发（不同参数，全冷） | 总 **4812ms**，各自 2983 / 2764 / 4670ms |
| 前端代理链路 | 407ms / HTTP 200 |

结论：① 245ms 已贴近 392ms 的「框架地板」，说明缓存读取本身几乎不占时间，剩下全是拦截器/鉴权/序列化；② 3 路并发总耗时 ≈ 最慢那条，说明扩容后没有排队（若仍是 6 线程池，18 个任务会串成三批，总时长接近 3 倍）；③ 返回数据未被改坏：`total=470 / failed=20 / users=67 / avgMessages=15.51`，与页面截图一致。

依赖侧无需改动：`smartop-service/admin/pom.xml:91-92` 已有 guava，根 pom `<guava.version>30.0-jre</guava.version>`（根 `pom.xml:66`），`Cache`/`CacheBuilder` 可正常解析；`mvn` 全量编译 892 个源文件 BUILD SUCCESS。

## 3. 本地启动的两条环境事实（Windows）

- `mvn spring-boot:run` 在本机会撞命令行长度上限 `CreateProcess error=206`；改用 `mvn package` + `java -jar`，约 **174 秒**起来。RabbitMQ（`10.122.12.186:5671`）连不上，只产生后台重试日志，不影响业务接口。
- 用 `java -jar` 后台起实例会长期占用 **8082**，此时在 IDEA 里 Run `AdminApplication` 会报端口占用（本次已 kill pid 24236 释放）。

## 4. 顺带发现的两个既有 bug（非本次引入，接口仍 200 但数据块为空）

后端日志里被 `catch` 吞掉的两类异常：

1. `Parameter 'chatbiMode' not found` —— `ChatbiEventQueryMapper.xml` 写 `#{chatbiMode}`，Java 方法参数名却是 `mode`，MyBatis 绑不上；疑似某统计块长期为空的原因（该文件里 chatbiMode 相关引用 27 处）。
2. `missing FROM-clause entry for table "sn_profile"` —— 某条 SQL 引用了 `sn_profile` 别名但 FROM 里没有该表（`sn_profile` 相关引用 10 处，集中在 `ChatbiEventQueryMapper.xml:106-166`）。

两项均待排查，直接关系到对应数据块准确性。
